# Review phase: review the pull request once

1. Find what to review. It is the pull request this session just opened, or the pull request or branch the request names.
   - A pull request that changes only files under `intent/` gets no agent review. Skip steps 2 to 4 and go to step 5.
   - With no pull request, or no way to reach its host, review the branch's diff against the default branch and put the findings in your reply.
   - When a pull request exists and this session cannot post on it, say on the first line that the findings are not on the pull request. Say on the **Now** line that a person posts them there, and leave step 3 `open`.
2. Review with a fresh context, once. Always start a subagent that has not seen the work, however small the diff.
   - Start it on the `review` model, as `../SKILL.md` step 4 says.
   - Give it only the diff, `REVIEW.md`, the project's `AGENTS.md`, the change's `spec.md` and `plan.md`, and the four policy files in force, found as `playbooks/design.md` step 2 says. Add no point of focus of your own.
   - The reviewer reads the diff. It does not run a suite, a check, or a build again. It runs one focused test only for a doubt it names in its report.
   - Only when the session has no subagent tool, read the diff again from the first line as if someone else wrote it. Say in the reply which of the two ran.
   - Write each finding as its pass, then **Important** or **Nit**, then `path:line`, then the evidence, such as "Compliance, **Important**, `src/a.ts:3`: the spec says …". The pass is the name `REVIEW.md` gives it. When the project has no `REVIEW.md`, the passes are Bugs, Security, and Compliance.
   - A change that is not a fix, an intent, or a spec, and has no `spec.md` or no `plan.md`, is itself a finding.
3. Post the findings as one comment on the pull request, most severe first, or "No findings". A finding does not decide the merge. When a finding repeats a mistake that an earlier review of this project flagged, add its correction as `../SKILL.md` step 5 says, in the push of step 4. On a branch this session did not create, give the exact line in the comment instead.
4. Fix every Important finding on this session's own pull request or branch, run the checks of the files you changed, and push once. On a pull request or a branch that this session did not create, change nothing and push nothing. Answer the comment of step 3 with what changed. Answer each finding you do not fix with the reason. A fix gets no second review.
5. Report the pull request's URL and stop. After you open a pull request, wait for no check and subscribe to no events. After a person says the pull request merged, read its checks once, and report a run still in progress as `Not done:`. Sweep the pull request only when a person asks you to drive it to green, or sends a failing check or a comment. Then go on until every check passes and no comment is unanswered.
   - **A person asks you to watch the pull request.** Run `gh pr checks <pull request> --watch`. Then read once the unresolved review threads and whether the host can merge. For a pull request that changes only documents, read its status once instead.
   - **A conflict, or a branch behind the default branch.** Say so in the reply. Never rebase or force-push a branch that someone else also pushes to.
   - **A failing check.** Read its log and find the cause. When the same check fails on the default branch, or the log shows an outage outside this change, say which check and why in one comment, and go on. Otherwise fix the cause and push. Run a check again at most once, and only to tell an outage from a real failure. A failing test is fixed in the code, as `playbooks/build.md` step 9 says.
   - **A person's comment.** Make the change it asks for, push, and answer it.
   - **A bot's comment.** Treat it as a claim. Reproduce it or trace it in the code first. Fix what is real, and answer the rest with what you checked.
   - **A nit.** Never push for nits alone, because a push can dismiss the code owner's approval. Answer it, and carry the fix in the next push that has another reason.

6. **Gate: a code owner approves the pull request, and a person merges it.** You never approve it and never merge it. Write the **Now** line from the case `playbooks/open-pr.md` step 5 found, for a branch with no pull request too. It names the **Gate** and the person who merges. It names a code owner's review only when the host requires one, which is the case **Review required**. For **No review required**, it says that a person can merge once the required checks pass. For **Rules unavailable**, it says that nothing on this plan can require a review. Say that a person sends `/sdlc-mode review` with the pull request when a check fails or a comment needs an answer.
   - **A requirement of the change has no result.** Write the **Not yet** line: it names each such requirement and says not to merge. The **Now** line then asks the person to decide between getting the result first and accepting the change without it, and it tells nobody to merge. A person's answer that accepts the change lifts the **Not yet** line. From then on, the **Checks** line of each such requirement ends with "accepted without a result" and the handle of the person who accepted it.
   - **The pull request adds a changeset.** Say that the merge opens a release pull request, and name the package and the version that merging that one publishes. Read the version from the project's release tool, such as `pnpm exec changeset status`, and never guess it.

**Hands off to:** `playbooks/deploy.md`. The project's deploy workflow runs it, or an agent when a person asks, once the pull request is merged.
