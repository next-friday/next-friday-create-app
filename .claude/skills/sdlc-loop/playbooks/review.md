# Review phase: drive the pull request to its gate

1. Find the pull request. It is the pull request this session just opened, or the one the request names.
   - Never review a diff yourself, and never start a subagent to review one. The host reviews every pull request as `REVIEW.md` says, in one of two ways. The project's `Claude review` workflow posts its findings as one comment that starts with `## Claude review`. A review service of the agent tool's maker, when the organization turned one on, posts its own check run and comments, as the project's `SETUP.md` says.
   - With no pull request, say that the review runs on the host once the branch has a pull request, and go to step 6.
2. Read the review's findings once they are there. They arrive minutes after a push, so never wait for them in this turn: step 5 says how the session learns of them.
   - **Neither reviewed the pull request.** The run of `Claude review` was skipped or the project has no such workflow, and the pull request has no check run of a review service. Write the **Not yet** line: it says that no review ran, and why. The repository variable `CLAUDE_CI_ENABLED` is not `true`, the pull request is a draft or comes from a fork, or the workflow file is missing.
   - **The run failed.** Read its log, and say the cause in the reply.
3. Treat each finding as a claim, as step 5 says for a bot's comment. A finding does not decide the merge. When a finding repeats a mistake that an earlier review of this project flagged, add its correction as `../SKILL.md` step 5 says, in the push of step 4. On a branch this session did not create, give the exact line in an answer to the comment instead.
4. Fix every Important finding that is real on this session's own pull request or branch, run the checks of the files you changed, and push once. On a pull request or a branch that this session did not create, change nothing and push nothing. Answer the review with what changed. Answer each finding you do not fix with the reason. The push starts a new review: handle its findings the same way once, and after that push nothing more for a finding until a person asks.
5. Report the pull request's URL, and watch a pull request this session opened. After a person says the pull request merged, read once the checks of the pull request's last commit and the run the merge started on the default branch. The change is done when the pull request's checks passed. A run still in progress on the default branch does not make the reply `Not done:`. Name it on the **Not yet** line, because a promotion waits for it, as `playbooks/deploy.md` step 1 says.
   - **The merged pull request added an `intent.md` or a `spec.md`.** Once you read from the host that it merged, ask the person whether to start the next playbook, as one choice asked through the question picker, as `../SKILL.md` step 6 says. For an intent, ask whether to write its spec now, which is `playbooks/design.md`. For a spec, ask whether to write its build plan now, which is `playbooks/build.md`. Name the change in the question, and put the answer that starts the playbook first. On that answer, read the playbook and run it in the same turn. On the other answer, write the reply, and give on the **Now** line the message that starts the playbook later.
   - **The session lists a tool that subscribes it to a pull request's events.** Call that tool once for the pull request. The host then wakes the session when a check ends or a comment arrives. On each wake, handle what arrived as the cases below say, without being asked, until every check passes and no comment is unanswered. When the tool's result says another agent already holds the pull request's events, say that this session does not watch it.
   - **The session lists no such tool.** Wait for no check. Say that nobody watches the pull request, and that a person sends `/sdlc-review` with it when a check fails or a comment needs an answer.
   - Never wait for a check in a sleep, and never write a loop of your own that polls the host for one.
   - **A person asks a session with no such tool to watch the pull request.** Run `gh pr checks <pull request> --watch`. Then read once the unresolved review threads and whether the host can merge. For a pull request that changes only documents, read its status once instead.
   - **A conflict, or a branch behind the default branch.** Say so in the reply. Never rebase or force-push a branch that someone else also pushes to.
   - **A failing check.** Read its log and find the cause. When the same check fails on the default branch, or the log shows an outage outside this change, say which check and why in one comment, and go on. Otherwise fix the cause and push. Run a check again at most once, and only to tell an outage from a real failure. A failing test is fixed in the code, as `playbooks/build.md` step 9 says.
   - **A person's comment.** When the host marks its author as an owner, a member, or a collaborator of the repository, make the change it asks for, push, and answer it. Answer any other person's comment, and change nothing for it until such a person asks.
   - **A bot's comment.** Treat it as a claim. Reproduce it or trace it in the code first. Fix what is real, and answer the rest with what you checked.
   - **A nit.** Never push for nits alone, because a push can dismiss the code owner's approval. Answer it, and carry the fix in the next push that has another reason.

6. **Gate: a code owner approves the pull request, and a person merges it.** You never approve it and never merge it. Write the **Now** line from the case `playbooks/open-pr.md` step 5 found, for a branch with no pull request too. It names the **Gate** and the person who merges. It names a code owner's review only when the host requires one, which is the case **Review required**. For **No review required**, it says that a person can merge once the required checks pass. For **Rules unavailable**, it says that nothing on this plan can require a review. Say that a person sends `/sdlc-review` with the pull request when a check fails or a comment needs an answer.
   - **A requirement of the change has no result.** Write the **Not yet** line: it names each such requirement and says not to merge. The **Now** line then asks the person to decide between getting the result first and accepting the change without it, and it tells nobody to merge. A person's answer that accepts the change lifts the **Not yet** line. From then on, the **Checks** line of each such requirement ends with "accepted without a result" and the handle of the person who accepted it.
   - **The pull request adds a changeset.** Say that the merge opens a release pull request, and name the package and the version that merging that one publishes. Read the version from the project's release tool, such as `pnpm exec changeset status`, and never guess it.

**Hands off to:** `playbooks/deploy.md`. The project's deploy workflow runs it, or an agent when a person asks, once the pull request is merged.
