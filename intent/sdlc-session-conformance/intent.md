# Intent: Make an sdlc-mode session follow its playbook and claim only what it proved

Author: @joetakara (Developer Productivity). Status: accepted.

## Problem

Two sessions, each in a project generated by 10.1.2, took one change through intent, spec, and build with `/sdlc-mode`, and then each audited itself against the playbooks from its own transcript. Both ran on the models their rule named. One took 56 minutes and the other 94, for changes of the same kind: add app skeletons to a workspace. The audits found the sessions departing from the playbooks in ways no check caught, and reading the same playbooks in opposite ways. The file and line references below are to `plugins/sdlc/source/skills/sdlc-mode/` and to `templates/` on `main`. An item says "both" when both audits show it, and "one" when one does.

What a session claimed beyond its proof:

1. Both answered `Done.` while CI on `main` was still in progress. One also had two of the spec's requirements that had never run, because no container image was built on the machine or in CI, and `pnpm test:e2e` failing for one app. `SKILL.md:78` defines `Done.` by "the merged pull request and its final checks", and `playbooks/review.md:13` says to "wait for no check", so a session that follows one breaks the other.
2. Both wrote a step as `done` that was not: one "Verify the work yourself" with a failing end-to-end test (`playbooks/build.md:35`, "Every check must pass"), the other a step of `playbooks/review.md` that did not apply to it. `SKILL.md:124` has the step's first sentence copied word for word, and the first sentence of `playbooks/review.md:12` is the case that does not apply.
3. One wrote, committed, and pushed the spec before its `explore` subagent reported, against `SKILL.md:44`, and its reply said the file list came from that subagent.
4. One named a code owner's review in its **Now** line after the host had answered that no rule can require one (`playbooks/review.md:20`).

Where a person's gate carried no decision:

5. The two sessions asked 19 questions. The person answered every one with an option the session had marked as recommended, most within seconds, and in one question every option carried that mark. `playbooks/intent.md:8` says an inferred answer "does not count", and does not say whether a recommended option the person picks is the originator's own words.
6. Neither asked what is out of scope, and neither had the problem in the person's own words: both inferred them from a table of folders. One added an out-of-scope item the person had not said. One asked a question the project's `README.md` already answered, and both wrote open questions a search of the repository answers.
7. The two sessions read the review rule in opposite ways. One reviewed no intent or spec pull request. The other reviewed all three of its pull requests, and those three reviews were its three largest costs: 279, 358, and 536 seconds, and 239,000 output tokens. Its review of the intent ended after the person had merged it, with a finding nobody could then act on. `playbooks/open-pr.md:25` says to go on to `playbooks/review.md`, `playbooks/review.md:6` says "Always start a subagent", and `playbooks/intent.md:18` and `playbooks/design.md` say to stop.

Where a session spent time and tokens for nothing:

8. Neither had a way to wait for a subagent. `SKILL.md:44` says to wait and not to end the turn, and does not say how. One polled 29 times while its `verifier` ran for 712 seconds, and those requests re-read about 10.7 million tokens of context. The other waited in fixed sleeps of about four minutes, so four reports reached it 378 seconds late in all, and a message the person typed sat unread for 2 minutes 38 seconds.
9. In both, the `verifier` and the reviewer ran again checks the session had already run; in one this took 153 seconds. `playbooks/build.md:36` gives the `verifier` no list of what ran.
10. Both ran by hand checks that `pnpm verify` or the `pre-push` hook also ran: 193 seconds in one, 84 in the other.
11. Both searched the whole tree themselves, where `SKILL.md:39` hands a sweep to `explore`. One never started an `explore` subagent.

Where the playbooks, the hooks, and the template disagree:

12. `SKILL.md:36` says to write each file "never with a shell command", and `templates/turborepo/README.md` tells the engineer to copy an app with Turborepo's generator, which writes files from the shell. Both sessions used the generator, and one wrote a scratch file with a shell heredoc.
13. `templates/turborepo/README.md:51` says adding an app "changes no root file except `prettier.config.ts`". `templates/turborepo/turbo.json:3` sets `"concurrency": "3"`, so `pnpm dev` stops at a fourth persistent task, and `templates/base/.claude/settings.json:19` denies the agent the edit of `prettier.config.ts`. Both sessions hit both. One lost about 216 seconds to the first. At the second, both had to stop for a person in the middle of the build, and one met the denial 30 minutes before it asked.
14. `templates/turborepo/AGENTS.md` gives `Tasks:    N successful, N total` as the healthy output in seven places, with counts that are wrong once the number of apps changes. Both sessions edited them by hand.
15. The reviewer has no role in the models rule. One session ran it on the main model and the other on the `explore` model, and both put their own points of focus in the reviewer's prompt, where `playbooks/review.md:6` names what the reviewer gets.
16. `playbooks/build.md:13` says to use the agent tool's plan mode when it has one. Neither session used it. `templates/base/.claude/settings.json:4` sets `"defaultMode": "plan"`, and both sessions ran in the normal mode.
17. `playbooks/build.md:35` says "Every check must pass", and `AGENTS.md` leaves `pnpm test:e2e` out of `pnpm verify`. Neither says what an end-to-end test that fails for want of a database on the machine counts as. Both sessions met it, and one ran the tests five times.
18. One session's shell gate blocked a command that only read `.claude/settings.json`.
19. One session reported each edit of a `.ts` or `.tsx` file taking 5 to 13 seconds, 117 seconds in all, and put it down to `templates/base/.agents/hooks/agent-format-after-edit.sh:11`, which runs `eslint --fix` on the file. The hook records no time, so this is that session's inference, and the other session did not report it.

What a session did to the machine without asking:

20. Both ran a `pkill -f` on a process name, which ends every matching process on the machine. One installed a browser of about 107 MiB. The other started a virtual machine for containers, pulled two images, and wrote two files to the agent's memory folder.

Where the template runs one check in several layers (read from the `turborepo` stack on `main`):

21. `templates/base/.husky/pre-push` runs `pnpm check` on every push, whatever changed. `pnpm check` is `verify:static`, `test:changed`, and `build`. Six pushes in the two sessions changed only files under `intent/` and took 47 to 59 seconds each. CI's "Detect Changes" job skips "Static Checks, Tests & Build" for such a pull request, so the hook on the machine does more than CI does.
22. `templates/turborepo/AGENTS.md` tells the agent to run the build, the tests, and the static checks before it reports a task complete, and the `pre-push` hook then runs nearly the same set: `pnpm verify` and `pnpm check` differ only in `test:coverage` against `test:changed`. This rule and the hook together are what made item 10.
23. ESLint with `--fix` and Prettier run on one file up to four times: in `agent-format-after-edit.sh` after each edit, in `lint-staged` at the commit, over the whole repository at the push, and in CI. The first two run the same commands on the same file.
24. `pnpm rules:check` runs in `pre-commit` and again inside `pnpm check` at the push.

What two `/setup-sdlc` sessions in the same projects reported about the same harness:

25. The reply-shape Stop hook sent a session's reply back for a **Checks** section after the session wrote the models rule in the person's home directory, while `git status --short` in the project was empty. `/setup-sdlc` writes that rule on every run, so the skill meets its own hook, and the session then ran the build, the tests, and the static checks, which prove nothing about that file.
26. The end of `pnpm verify`'s output showed only the build's summary, so a session could not read each step's result from it and ran the steps again one at a time. Both audited sessions read only filtered lines of it as well, and when a step in the middle failed, one could not see the steps after it.
27. The checks a session ran itself came back from Turborepo's cache (`2 cached, 2 total`), so they were not fresh runs; only the `verifier`, which set `TURBO_FORCE=true`, ran them anew.

Where the harness does more than the AI-native SDLC Playbook asks, and the surplus is where the sessions waited:

28. **Checks at the push.** The playbook puts heavy checks in two places: "build-phase hooks should be fast and scoped to the file that changed. Heavier checks such as the full test suite belong at the commit or the PR" (page 27). It names no check at the push. The harness runs the whole static set, the tests, and the build there (item 21).
29. **What the verifier does.** The playbook's `verifier` reads: "Start the app with make run. Exercise the changed behavior and the two nearest neighboring flows. Report what you ran, what you saw, and any behavior that does not match plan.md. Do not fix anything; report only" (page 29), and it is "one way to package the final check by running a fresh context window once the session believes the work is done" (page 31). The harness's `verifier` also ran the static checks, the tests, and the build again (item 9).
30. **Where the review runs.** The playbook runs the review on the pull request, outside the session: "The managed Code Review service is the fastest start. An admin enables it and selects repositories. Run the review in your own CI with the claude-code-action when you need control of the pipeline" (page 38). The harness has the session start a reviewer and wait for it (item 8).
31. **The interview.** The playbook's originator "may describe what they cannot do today, who is affected by the idea, what better looks like, or what is out of scope. No formal language is required", Claude then asks "the questions an analyst would ask", and "The originator corrects anything Claude misunderstood" (page 12). The harness requires all five things and one question at a time (items 5 and 6).
32. **Review of an intent or a spec.** The playbook has the product owner review the spec "against the idea" (page 16) and names no agent review of either pull request. The harness's playbooks disagree on it (item 7).

The playbook says nothing on how a session waits for a subagent, and nothing on what `Done.` means when CI skips a job; items 1 and 8 are the harness's own to settle. It does ask for the edit hook the harness has: "Run the formatter and linter after file edits so drift never accumulates" (page 27), so item 19 is about that hook's speed, not its place.

What only the second audit showed:

33. `playbooks/build.md:30` sends a check that fails a second time to `advise`. One session had ESLint fail three times running and the end-to-end tests fail three times running, and started no `advise` subagent. `SKILL.md:40` and `playbooks/build.md:30` do not say whether a failure of the machine, such as a missing database, counts.
34. `SKILL.md:11` says to write **Request** again in the reply, and `SKILL.md:122` says "only in the first reply of a task". `SKILL.md:34` leaves **Steps** out of "a reply that stops in a few lines", and `SKILL.md:124` puts it in "every reply of the task". Both sessions left **Steps** out of their short replies after a gate, and one left **Request** out of a reply.

37. `playbooks/open-pr.md:3` says to "Name the branch as the project's contributing guide says", and `templates/turborepo/CONTRIBUTING.md` gives no form for a branch name; only the `pre-commit` hook's message does.

39. The harness has no way to watch a pull request when a person asks for it. `playbooks/review.md:13` says to "wait for no check and subscribe to no events", and to sweep the pull request "only when a person asks", and names no tool for that sweep. One session read CI by waiting 202 seconds in a sleep.

What `mattpocock/skills`, a second community repository, does where the harness struggled:

40. **Questions in rounds.** Its interview asks every question it can ask without guessing at an open answer in one round: "Ask the whole frontier in one round: number each question and give your recommended answer", and "Word each question so \"yes\" accepts your recommended answer" (`skills/productivity/grilling/SKILL.md`). The harness asks one question, waits, and asks the next (`SKILL.md:46`), which made 19 round trips in the two sessions.
41. **No picker for an interview.** It asks in plain chat text and refuses the agent tool's question picker: "Structured pickers push the model towards multiple-choice questions with pre-baked answers, which is the opposite of what grilling is for: open questions you answer in your own words" (`.out-of-scope/native-question-tool.md`). Both sessions asked all 19 questions through the picker, and item 5 is what came of it.
42. **Facts are the agent's to find, without blocking.** "Finding facts is your job, never the user's", and while a search runs, "only the questions downstream of it wait for the sub-agent to report; ask the rest of the frontier now" (`skills/productivity/grilling/SKILL.md`). Item 6 shows a question the repository answered.
43. **The reviewer runs in the foreground and skips what tools enforce.** "Issue both sub-agent calls together, in the foreground, and aggregate the reports they return", each report "Under 400 words", and "Skip anything tooling enforces" (`skills/engineering/code-review/SKILL.md`). The harness's reviewers ran in the background, ran the static checks again, and one wrote 103,000 output tokens.
44. **The full suite runs once.** "Run typechecking regularly, single test files regularly, and the full test suite once at the end" (`skills/engineering/implement/SKILL.md`). Items 9, 10, and 22 show it run by the session, its `verifier`, and the hook.
45. **A rule says what to do.** "steering by prohibition drags the forbidden behaviour into context and makes it more available, not less", so "Prompt the positive: state the target behaviour" (`skills/productivity/writing-for-agents/SKILL.md`). The same file calls a document that restates what a command prints a cache that goes stale, which is item 14.

What `obra/superpowers`, a third community repository, does where the harness struggled:

46. **A claim needs a run in the same message.** "If you haven't run the verification command in this message, you cannot claim it passes", and its table sets "Requirements met" against a "Line-by-line checklist", with "Tests passing" marked not sufficient (`skills/verification-before-completion/SKILL.md`). Item 1 is the claim made without it.
47. **A reviewer does not run the suite again.** "The implementer already ran the tests and reported results with TDD evidence for exactly this code. Do not re-run the suite to confirm their report. Run a test only when reading the code raises a specific doubt that no existing run answers" (`skills/subagent-driven-development/task-reviewer-prompt.md`). Item 9 is the suite run again.
48. **The reviewer's model is named, and the cheapest is not the floor.** "Turn count beats token price", and "Use a mid-tier model as the floor for reviewers" (`skills/subagent-driven-development/SKILL.md`). The two sessions bear it out on one change each: the reviewer on the main model took 67 seconds and 7,800 output tokens, and the three on the `explore` model took 279 to 536 seconds and 59,000 to 103,000 output tokens each (items 7 and 15).
49. **An open question comes before any option.** "Until you know why they want it, ask open questions, with no example answers attached. Their own words carry intent that your options can't", "Options steer. Ask them to describe it first", and "Only what they said goes in as theirs. Anything you filled in goes in as your proposal, with your reason" (`skills/brainstorming/SKILL.md`). On options it goes further than item 40, which puts a recommended answer beside every question.

What the originator saw in a workspace of several apps:

50. In the `turborepo` stack, CI checks only the apps a change affects, and the machine checks them all. `templates/turborepo/.github/workflows/ci.yml` sets `TURBO_FILTER=--affected` and `TURBO_SCM_BASE` before its checks, and the root scripts read `$TURBO_FILTER`. The `pre-push` hook and the commands `AGENTS.md` gives the agent leave it unset, so a change to one app builds, tests, and type-checks every app on the machine. `AGENTS.md` shows the filter for one case only, "Tests in one app". ESLint, Prettier, Knip, and `sort-package-json` run once over the whole workspace whatever the filter says.

## Proposed outcome

A session that runs a playbook does each step the playbook names, and a reply states only what the session proved in that turn.

1. **Done means proved.** `Done.` and a `done` step are written only when every requirement has a result read in that turn. A check that could not run, a job CI skipped, and a run still in progress each keep the reply at `Not done:`, with the reason. A requirement is read off one by one against its result, as item 46 says; passing tests alone do not make it met.
2. **A reply matches the order of the work.** A session does not write from a subagent's report before the report arrives, and does not credit a source it did not use.
3. **A gate holds a person's own words.** The interview has two kinds of question. What the problem is, why it matters, and what is out of scope are asked open, in plain chat text, with no answer offered, so the words are the person's (item 49). A choice between ways is asked in rounds, each round every question that needs no open answer, numbered, in plain text and not through the question picker, with the answer the session recommends beside it (items 40 and 41). The session finds facts itself and asks only what the request and the project leave open. The artifact holds what the person said as theirs and what the session filled in as its proposal, marked as such. The originator took this on the agent's recommendation; the split into two kinds is the agent's own, and neither repository writes it this way. What still counts as said is open question 1.
4. **One wait, no polling, no fixed sleep, no check-in message.** The rule states what to do first, as item 45 says: a session that needs a subagent's report takes it from one call that returns it, and the reviewer runs in the foreground as item 43 shows. Behind that target stand three guard rails. While a subagent runs, a session does not poll for it, does not sleep for a fixed time, and does not message it to ask how it is doing. The originator took these three from `pstack` in the `cursor/plugins` repository: "Call no scripts, run no polling loops, and never relay messages or status between agents", and "Never message one to check on it, because a message restarts an idle agent" (`pstack/skills/poteto-mode/playbooks/orchestrate.md`). The session goes on when the report arrives, and does not hold back a message the person sends meanwhile.
5. **A check runs once.** A session, its `verifier`, and the hooks do not each run the same check on the same tree. `AGENTS.md` and the hooks name one owner for each check, and the agent takes the hook's result as its proof for the checks the hook owns. The `verifier` runs the app and exercises the change, and the reviewer reads the diff; neither runs the suite again without a doubt it can name (items 29, 43, and 47).
6. **The push hook does what the change needs.** A push that changes only documents does not lint, type-check, or build the apps, and the hook and CI decide that by the same rule. In the `turborepo` stack, the hook and the agent's own checks cover the apps the change affects, as CI's do, and every app when the change touches a root file.
7. **The playbooks agree with each other and with the template.** Items 1, 2, 7, 12 to 17, and 33 to 37 each have one answer, written where the session reads it, so two sessions cannot read one rule in opposite ways.
8. **Adding an app works as the README says.** In the `turborepo` stack, `pnpm dev` starts every app after one is added, and the plan names beforehand each file the agent may not edit.
9. **The session leaves the machine alone.** It ends only the processes it started, and asks before it installs or starts anything outside the project or writes a file there.
10. **The reply-shape hook asks for checks only when the project changed.** A session that changes no file of the project is not sent back, and `/setup-sdlc` ends in one reply.
11. **One read of `pnpm verify` shows every step.** Its last lines name each step and its result.
12. **The review stays in the session.** The session starts the reviewer and waits for its report in one call, without polling. The originator chose this over a review on the pull request, which needs a Claude Team or Enterprise plan or `claude-code-action` in CI; the project this harness is used in has neither. Item 30 is the one surplus that stays. The reviewer gets a role of its own in the models rule, so two sessions do not choose differently; which model is open question 21.
13. **The harness asks for no more than the playbook does.** Where items 28, 29, 31, and 32 show a surplus, the harness drops it or the intent's spec gives the reason it stays.
14. **A program watches a pull request, and only when a person asks.** When a person asks the session to watch a pull request, a command polls the host and returns once at a verdict; the session sends no request while it waits. The originator took this from `pstack`: "Babysitting starts when the user asks for it", "Watcher output drives wakeups. Never add a second sleep loop" (`pstack/skills/poteto-mode/playbooks/babysit.md`), and "Watch each PR with PR and CI event subscriptions when your harness has them" (`pstack/skills/poteto-mode/playbooks/orchestrate.md`). A pull request that holds only documents gets one status read, not a watch.

This change ships before the one in `intent/first-pull-request-ci/`, by the originator's decision: the harness is repaired first.

The hooks keep what only they can do: the secret scan before a commit, the commit message check, and the refusal to commit or push on `main`.

Out of scope: the models rule, which the session followed; a second models rule of another tool on the person's machine; and the first pull request's checks and the setup at creation, which `intent/first-pull-request-ci/` holds.

## Constraints

- The AI-native SDLC Playbook is the source for what the harness requires; a step it does not name needs a person's decision to stay.
- A review that runs on the pull request needs the managed Code Review service, which a Claude Team or Enterprise plan offers, or `claude-code-action` in CI with a token; a project with neither still needs a review.
- The gates stay where they are: a person corrects the intent, accepts the intent, the spec, and the plan, approves the pull request, and merges it.
- A wording change to a skill or a playbook is tested as `AGENTS.md` says, and the eval runs are ordered by the product owner, who has stopped spending on them.
- A number in a playbook, such as a time limit, needs a person's decision or a source.
- The hooks and settings named above are files a person commits.

## Open questions

1. Whether a "yes" to an answer the session recommended counts as the originator's own words. Rounds in plain text cut the round trips and remove the picker, and they still let a person accept every recommendation with one word.
2. Whether the intent and the spec pull requests get the review of `playbooks/review.md`, or stop at their gate without one.
3. What a session does instead of polling and sleeping. `pstack` starts every subagent in the background and takes the agent tool's notice when one finishes ("Subagents run in the background by default and notify you when they finish", `pstack/docs/harness/claude-code.md`), which means the turn may end while a subagent runs, against `SKILL.md:44`. The other way is to start the `verifier` and the reviewer in the foreground, so one call returns the report in the same turn. Neither has been tried here. Not checked: whether a turn that ends is woken by the notice in a run with no person, such as a CI job or an eval, and whether a foreground call has a time limit shorter than a `verifier` run.
4. Which checks the `verifier` runs when the session has run some, and whether a check answered from Turborepo's cache counts as run.
5. Whether a skipped CI job, a check the machine cannot run, and a run still in progress each block `Done.`, or only some of them.
6. Whether the generator of item 12 is an exception to the file-editing rule, and whether a generator that fails twice is the "check" that `playbooks/build.md:30` sends to `advise`.
7. What `turbo.json` sets for `concurrency`, and whether `prettier.config.ts` stays denied to the agent when the README requires its edit.
8. Whether the `eslint --fix` of item 19 is the cause of the slow edits; the hook has not been timed.
9. Which of these a hook or a script can check, and which only an eval case can. No case covers them today.
10. Whether the figures hold. Each comes from a session's reading of its own transcript, which nobody else has checked, and the two sessions ran on one machine at the same hour for the same person.
11. Which layer owns each check: the edit hook, the commit, the push, the agent's own run, or CI. Items 21 to 24 were read from the `turborepo` stack; the other four stacks share the hooks of `templates/base`, and their `check` scripts were not read.
12. How the push hook learns what changed, so that it and CI's "Detect Changes" cannot disagree.
13. Whether the agent still runs the whole of `pnpm verify` before a push, or learns of a failure only from the hook.
14. Why the reply-shape hook fired in item 25 when the project's tree was unchanged. The hook has looked only at the project folder since 10.1.2, the version that project was generated by; its input in that session has not been read.
15. What the last lines of `pnpm verify` print, and whether a step answered from Turborepo's cache is marked as such.
16. Whether the push hook keeps any check, given item 28, and what then stops a broken branch before CI does.
17. Whether a check that fails for a reason of the machine counts toward the two failures that send a session to `advise`.
18. Where the team on an intent's author line comes from, and what a spec quotes when the request is not in the language the files are written in.
19. Whether a requirement that only a container image proves is checked on the machine when CI is set to build none.
20. What watches the pull request of outcome 14. `pstack` ships its own watcher, about 2,400 lines and 1,200 more of tests, which needs `bun` and serves stacks of pull requests the harness does not have. It decides from five things in order: a merge conflict, unresolved review threads, failing checks, a review that requests changes, and a merge the host blocks (`pstack/skills/poteto-mode/scripts/watch-pr/policy.ts`). The host's own `gh pr checks --watch` looks only at the checks, so a pull request with green checks and an open review thread would read as ready. Claude Code's `/autofix-pr` starts a cloud session subscribed to the pull request and needs the Claude GitHub App on the repository. None has been run here, and only the deciding lines of `policy.ts` were read.
21. Which model the reviewer's role names. Item 48 points at the main model over the `explore` model, from one change in each of two sessions and one community rule; no run has compared them on the same diff.
22. How the machine scopes a check to the affected apps: the same `--affected` CI uses needs `origin/<base>` fetched, and what Turborepo treats as affecting every app, such as a root file or the lockfile, has not been checked against the installed version's documentation. Whether the workspace-wide checks of item 50 can be scoped at all, and what that would save, has not been measured; in the two sessions Turborepo's cache already answered the unchanged apps.
